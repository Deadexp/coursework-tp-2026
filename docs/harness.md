# 4. Настройка harness

**Harness** — всё, что окружает модель и превращает её в агента для нашего проекта: инструкции, разрешения, автоматические действия, готовые сценарии и вспомогательные агенты. Всё, кроме личных настроек, хранится в репозитории, поэтому у всех трёх участниц агент работает одинаково.

| Компонент | Файл | Зачем |
|---|---|---|
| Инструкции проекта | `CLAUDE.md` | Архитектура, правила и команды; агент читает файл в начале каждой сессии |
| Разрешения | `.claude/settings.json` → `permissions` | Что агент делает сам, что только с подтверждением, что запрещено |
| Хук автоформатирования | `.claude/settings.json` → `hooks`, `.claude/hooks/format.sh` | После каждой правки файла приводит его к единому стилю |
| Скилл `/verify` | `.claude/skills/verify/SKILL.md` | Полная проверка проекта перед Pull Request одной командой |
| Субагент `db-reviewer` | `.claude/agents/db-reviewer.md` | Отдельный ревьюер изменений схемы БД |
| Личные настройки | `.claude/settings.local.json` (не в git) | Если участнице нужно что-то поменять только у себя |

## Инструкции проекта — `CLAUDE.md`

Разделы: архитектура, структура backend, база данных, учебный контент, словарь и повторение, фронтенд, авторизация, команды, соглашения.

Главное в этом файле — правила, которые появились **после ошибок агента** (см. журнал в `docs/agent-choice.md`). Агент не помнит прошлые сессии, а `CLAUDE.md` читает каждый раз, поэтому урок закрепляется:

| Правило | Откуда взялось |
|---|---|
| В `downgrade` миграции удалять созданные ENUM-типы | Откат первой миграции ломал повторное применение |
| Новую модель импортировать в `app/models.py`; тест `test_app_startup.py` это проверяет | Ошибка 500 на живом сервере, которую не видели тесты |
| Производные значения (прогресс, статистика) не хранить — 3НФ | Требование к схеме БД |
| Правильные ответы клиент получает только после попытки | Иначе их можно подсмотреть в браузере |
| Контракт API для бота — `docs/api-vocabulary.md`, обновлять при изменении API | Сайт и бот должны работать с одними правилами |

## Разрешения

Агент выполняет команды на компьютере пользователя, поэтому каждая команда проходит через список разрешений:

| Уровень | Команды | Почему |
|---|---|---|
| **Без подтверждения** | `docker compose`, `npm run`, `npm install`, `pytest`, `ruff`, `alembic`, `git status / diff / log` | Повседневная работа: запуск, тесты, миграции, просмотр изменений. Подтверждать каждую — только мешать |
| **С подтверждением** | `git push`, `docker compose down -v` | Отправка кода на GitHub видна всей команде; `down -v` удаляет базу данных со всеми данными |
| **Запрещено** | Чтение и изменение `.env` | В файле токены и пароли — они не должны попасть в диалог с моделью |

Запрет сработал на практике: агент попытался создать `.env` сам, получил отказ, и файл создал сам пользователь.

## Хук автоформатирования

Срабатывает после каждой правки файла агентом (событие `PostToolUse` для инструментов `Write` и `Edit`):

- **Python** — `ruff check --fix` и `ruff format`. Если `ruff` не установлен на компьютере, хук запускает его внутри контейнера сервера;
- **TypeScript, CSS, JSON** — `prettier`.

Хук никогда не блокирует правку: если форматтер недоступен, он просто пропускает файл.

**Как проверено:** в файл намеренно вносилось нарушение стиля обычной правкой агента, после чего файл проверялся. Для TypeScript (испорченные кавычки) хук сработал сразу. Для Python проверка при написании этого документа показала, что хук **ничего не делал** — `ruff` был только в контейнере. Хук исправлен и проверен повторно: лишние пробелы в `MIN_EASE   =    1.3` исчезли сразу после правки.

## Скилл `/verify`

Готовый сценарий проверки, который агент выполняет по команде `/verify` или сам — перед открытием Pull Request:

1. backend: формат, линтер, 41 тест;
2. модели и миграции совпадают (`alembic check`);
3. сайт: формат, типы, линтер (0 предупреждений), сборка;
4. e2e-тесты в браузере;
5. удаление тестовых пользователей из базы.

Отдельное правило: не называть проверку успешной, если шаг пропущен или упал. Все шаги прогнаны вручную при создании скилла.

## Субагент `db-reviewer`

Отдельный агент со своей инструкцией и только инструментами чтения: он не может править код, только сообщает замечания. Вызывается после изменения моделей или миграций и проверяет:

- нормализацию до 3НФ и описание осознанных отступлений;
- внешние ключи, `UNIQUE`, `CHECK`, `NOT NULL`;
- что `downgrade` полностью откатывает `upgrade`;
- что новая модель зарегистрирована и документация `docs/database.md` обновлена.

Зачем отдельный агент: основной агент, который только что написал миграцию, склонен считать её правильной. Ревьюер получает свежий контекст и узкий чек-лист.
