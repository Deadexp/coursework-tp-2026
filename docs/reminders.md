# Напоминания в Telegram

Напоминания включаются только по желанию пользователя. По умолчанию они выключены,
время — **19:00**, часовой пояс — **Europe/Moscow**. Языковая модель не используется.

## Настройка

Сначала нужно связать Telegram с аккаунтом сайта. В подключённом боте откройте
`/reminders` или «⏰ Напоминания». Кнопка «Включить» включает ежедневную доставку,
«Выключить» отключает её. Кнопка «Изменить время и часовой пояс» последовательно
запрашивает время `ЧЧ:ММ` и имя пояса IANA, например `Europe/Moscow`,
`Europe/Berlin` или `Asia/Yekaterinburg`. Ответ «оставить» сохраняет текущий пояс.
Изменение времени само по себе не включает напоминания. `/stop` отменяет незавершённый ввод.

Настройки сохраняются в PostgreSQL и доступны сайту и боту через один API.
При перезапуске бота настройки не теряются. Демо-режим уведомлений не отправляет.
Возможность редактирования на сайте использует тот же контракт, что и команда бота.

## Локальный запуск и время

Бот, API, база и доступ к интернету должны работать. При выключенном компьютере,
спящем ноутбуке или остановленном контейнере сообщение не придёт в выбранное время.
После восстановления бот проверяет просроченное расписание: доставка возможна
только в пределах **одного часа** от назначенного времени. Давние дни не рассылаются.
Это окно может пересекать полночь; запись относится к дате назначенного напоминания.

Фоновая проверка выполняется каждые 45 секунд. Поэтому доставка не обещается
точно в первую секунду выбранной минуты. При сбоях интервал проверки увеличивается
до пяти минут. У каждой дневной доставки не более трёх попыток; после первой
сетевой ошибки следующая попытка возможна не раньше чем через минуту,
после второй — не раньше чем через три минуты, в пределах часового окна.
Ограничение Telegram `retry_after` также учитывается.

Расписание использует локальную дату и IANA timezone. При переводе часов назад
выбирается первое вхождение повторившегося времени. Если выбранного местного времени
нет из-за весеннего перевода часов, этот день пропускается. Для доступности базы
часовых поясов в разных ОС backend использует пакет `tzdata`.

## Контракт API

`GET /reminders/settings` и `PATCH /reminders/settings` принимают обычный JWT сайта
либо служебные заголовки бота `X-Service-Token` + `X-Telegram-ID`.
Идентификатор пользователя в теле запроса не принимается.

```json
{"enabled": false, "time": "19:00", "timezone": "Europe/Moscow"}
```

PATCH принимает любое подмножество этих трёх полей; `null`, неизвестные поля,
некорректное время и неизвестный timezone возвращают 422. Включение без привязанного
Telegram возвращает 409 с указанием сначала подключить аккаунт. Успешный ответ —
200 и полное текущее состояние. Если строка настроек ещё не создавалась, GET
возвращает значения по умолчанию и не пишет в базу.

Следующие маршруты предназначены только для доверенного процесса бота;
JWT пользователя не даёт к ним доступа:

| Маршрут | Запрос | Результат |
|---|---|---|
| `POST /reminders/claims` | `{"limit": 1}`; от 1 до 20 | Массив дневных доставок, атомарно закреплённых за worker |
| `POST /reminders/deliveries/{id}/ack` | `claim_token`, `outcome`; необязательные `retry_after_seconds`, `telegram_message_id` | `{"status": "sent"}` или текущее состояние доставки |

Оба маршрута требуют `X-Service-Token` (`BotService`). Получателя выбирает сервер;
произвольный `telegram_id` в запросе не принимается. Данные claim включают
`delivery_id`, случайный `claim_token`, служебный `telegram_id`, `local_date`,
`scheduled_at`. ACK принимает исходы `sent`, `retry`, `forbidden`, `failed`.
Эти служебные данные и секреты не показываются в пользовательском интерфейсе.

## Сохранность и пределы доставки

Таблица `reminder_settings` хранит пользовательский opt-in и расписание.
`reminder_deliveries` хранит попытки, срок аренды, результат и квитанцию отправки.
Уникальность `(user_id, local_date)` предотвращает вторую плановую доставку за
эту локальную дату. Блокировки PostgreSQL `FOR UPDATE SKIP LOCKED` разделяют
одновременные claims; аренда действует три минуты. После аварийной остановки
невыполненный claim может быть взят повторно. Новый claim получает новый случайный
token; запоздавший ACK со старым token отклоняется с 409.

После успешной отправки worker повторяет только ACK, если backend временно недоступен,
а не саму отправку. Повторный ACK с тем же token и исходом безопасен.
При `TelegramForbiddenError` (например, пользователь заблокировал бота) backend
отключает напоминания. Другие окончательно отклонённые сообщения не повторяются в этот день.

**Абсолютное exactly-once для Telegram не гарантируется.** Между принятием сообщения
Telegram и сохранением ACK существует граница двух независимых систем. При обрыве
сети ответ Telegram может потеряться, хотя сообщение доставлено; при падении процесса
после отправки может потеряться ещё не подтверждённая квитанция. Повтор такой попытки
в редком случае приводит к дублированию. Выбраны ограниченные повторы, чтобы не считать
неотправленное сообщение доставленным до вызова Telegram. После окончания часового
окна или исчерпания трёх попыток повторов в этот день нет.

Изменение расписания или выключение отменяет очередные pending/claimed записи.
Уже отправляемый сетевой запрос отменить надёжно невозможно: одно сообщение может
успеть прийти одновременно с выключением. Если доставка за локальную дату уже была
создана, повторное включение или изменение времени не создаёт вторую запись на эту
же дату; новое расписание начнёт действовать для следующей доступной даты.

Для одного Telegram-токена нужен один polling-процесс. Дополнительный worker не
является способом горизонтального масштабирования Telegram polling. Изменять
`.env`, перезапускать чужой экземпляр или использовать рабочий токен для тестов не нужно.

## Запуск и диагностика

При временной сетевой ошибке Telegram на старте процесс теперь остаётся запущенным
и повторяет соединение через 5, 10, 20, 40, затем не чаще раза в 60 секунд.
Логи сообщают публичное имя подключённого бота. Ошибка сети сама по себе не доказывает
правильность или неправильность токена. Ошибки авторизации/конфликта имеют отдельные
сообщения; автоматическая смена токена, удаление webhook и сброс данных не выполняются.
Форматтер скрывает настроенные секреты в сообщениях и traceback.

При штатной остановке polling фоновая задача отменяется и ожидается её завершение,
затем закрываются сессии Telegram и backend. Незавершённый claim восстанавливается
по сроку аренды, пока остаётся в допустимом окне доставки.

Тесты backend проверяют opt-in, авторизацию, часовые пояса/DST, конкурентные claims,
отключение, ежедневную уникальность, аренду, backoff и запрет устаревших ACK.
Тесты бота используют только подставные Telegram-сессии и HTTP transport, включая
ошибку ACK после успешной отправки и штатную отмену фоновой задачи. Они не обращаются
к реальным получателям или LLM.
