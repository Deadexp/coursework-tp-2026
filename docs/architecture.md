# 2. Архитектура системы

**Тип:** клиент-сервер. Сервер — **модульный монолит**: одно приложение и одна база данных, внутри разделённые на независимые модули.

```mermaid
flowchart LR
  User((Ученик))
  User --> Web
  User --> TG[Telegram]
  TG <--> Bot

  subgraph Clients[Клиенты]
    Web[Сайт<br/>React + TypeScript]
    Bot[Telegram-бот<br/>aiogram]
  end

  subgraph Server[Backend — FastAPI, модульный монолит]
    direction TB
    Users[users]
    Learning[learning]
    Vocabulary[vocabulary]
    Dialogs[dialogs]
    Recs[recommendations]
    LLMmod[llm]
  end

  Web -->|REST /api, JWT| Server
  Bot -->|REST, служебный токен| Server
  Server --> DB[(PostgreSQL)]
  LLMmod --> LLM[LLM-провайдер]
```

Главное правило архитектуры: **данными владеет только сервер.** Сайт и бот — два равноправных клиента одного REST API, бот не обращается к базе напрямую. Поэтому ответ, данный на сайте, и слово, повторённое в боте, попадают в одни и те же таблицы, и адаптивность работает по всей истории ученика.

## Компоненты и технологии

| Компонент | Технологии | Почему |
|---|---|---|
| Сайт | React 19, TypeScript, Vite, React Router | Отдельное SPA естественно ложится на клиент-серверную схему; TypeScript ловит ошибки в типах данных API до запуска |
| Сервер (API) | Python 3.12, FastAPI, Pydantic | Асинхронность (бот и запросы к LLM — асинхронные), автоматическая документация API (Swagger), строгая проверка входных данных |
| Работа с БД | SQLAlchemy 2.0, Alembic | Модели в коде, схема меняется только миграциями |
| База данных | PostgreSQL 16 | Обоснование — в `docs/database.md` |
| Telegram-бот | aiogram 3, httpx | Асинхронный фреймворк для ботов; httpx — клиент к нашему API |
| Языковая модель | Claude Sonnet 5.5 через официальный SDK `anthropic`; модуль `app/llm` с общим интерфейсом `LLMClient` | Ответы строго по схеме (structured outputs → Pydantic), провайдер подключается в одном месте; без ключа работает заглушка |
| Запуск | Docker Compose | Вся система поднимается одной командой одинаково у всех участниц |

## Модули сервера

| Модуль | За что отвечает | Таблицы | Состояние |
|---|---|---|---|
| `users` | Регистрация, вход, текущий пользователь | `users`, `telegram_link_codes` | Работает, включая одноразовую привязку Telegram |
| `learning` | Темы, упражнения, проверка ответов, запись ошибок по типам | `topics`, `exercises`, `exercise_answers`, `attempts`, `error_types`, `mistakes` | Работает |
| `vocabulary` | Личный словарь, интервальное повторение SM-2, трудные слова | `words`, `topic_words`, `user_words`, `word_reviews` | Работает |
| `dialogs` | Диалог с виртуальным носителем языка: 5 сценариев, ответы на уровне ученика, исправления ошибок, отзыв | `dialogs`, `dialog_messages` (+ `mistakes`) | Работает |
| `recommendations` | План занятия от адаптивного наставника по ошибкам, прогрессу и словарю | `lesson_plans`, `lesson_plan_items` | Работает |
| `llm` | Общий интерфейс к языковой модели, провайдер Claude, обработка ошибок и отказов | — | Работает |

Внутри модуля код разложен одинаково: `models.py` (таблицы), `schemas.py` (формат запросов и ответов), `service.py` (логика), `router.py` (адреса API). Модуль не лезет в таблицы другого модуля напрямую, а вызывает его `service.py`. Благодаря этому границы модулей можно превратить в границы сервисов, если когда-нибудь понадобится (см. ниже).

## Как проходит запрос

На примере ответа на упражнение — основного действия, на котором строится адаптивность:

```mermaid
sequenceDiagram
  actor U as Ученик
  participant W as Сайт
  participant A as API (FastAPI)
  participant L as learning.service
  participant D as PostgreSQL

  U->>W: выбирает ответ «eat»
  W->>A: POST /exercises/10/attempts<br/>Authorization: Bearer JWT
  A->>A: проверка токена → пользователь
  A->>L: submit_attempt(...)
  L->>D: варианты ответа упражнения
  L->>L: сравнение без учёта регистра, пробелов, точки
  L->>D: INSERT attempts (is_correct = false)
  L->>D: INSERT mistakes (тип ошибки «Present Simple»)
  A-->>W: верно / неверно, правильный ответ,<br/>объяснение, тип ошибки
  W-->>U: «Пока неверно… ошибка записана в навык»
```

Правильные ответы клиент получает **только в ответе на попытку**, никогда — вместе с заданием, иначе их можно было бы подсмотреть в браузере.

## Как работает ИИ

```mermaid
sequenceDiagram
  actor U as Ученик
  participant W as Сайт
  participant A as API (dialogs)
  participant C as Claude Sonnet 5.5
  participant D as PostgreSQL

  U->>W: «She don't drink coffee»
  W->>A: POST /dialogs/7/messages
  A->>D: история диалога, уровень, типы ошибок
  A->>C: системный промпт + история<br/>ответ строго по схеме SpeakerTurn
  C-->>A: {corrections: [...], reply: "..."}
  A->>A: проверка кодов ошибок по БД
  A->>D: INSERT dialog_messages, mistakes
  A-->>W: реплика Emma + исправления
```

- **Один запрос — и ответ, и разбор ошибок.** Модель возвращает не текст, а объект по схеме: реплику собеседника и список исправлений с типом ошибки. Ошибки из разговора попадают в ту же таблицу `mistakes`, что и ошибки из упражнений, поэтому наставник видит их вместе.
- **Наставник** получает уровень, прогресс по темам, слабые места за 14 дней с примерами и число слов к повторению и возвращает план по схеме. Ссылки на темы, которые предлагает модель, сервер проверяет по БД.
- **Скорость и качество.** Реплики чата идут без «размышлений» модели (замер: 1,8–2,6 с вместо 11–16 с), отзыв и план — с размышлениями, там важнее качество.
- **Надёжность.** Модель вызывается до записи в БД; ошибки API превращаются в ответ 503 с понятным текстом, отказ модели — в 422; при отказе по соображениям безопасности API само повторяет запрос на другой модели (`fallbacks`).

## Аутентификация

- **Сайт:** вход по email и паролю → сервер выдаёт JWT-токен, сайт прикладывает его к каждому запросу. Пароли хранятся только как хэш argon2. *Работает.*
- **Бот:** у бота нет пароля пользователя. Он обращается к API со **служебным токеном** (`BOT_SERVICE_TOKEN` из `.env`, заголовок `X-Service-Token`) и указывает, от имени какого Telegram-пользователя действует. Сервер находит ученика по `users.telegram_id`. *Реализовано для словаря: обязательны `X-Service-Token` и `X-Telegram-ID`; пустой и стандартный ключ отключают служебный доступ. Остальные модули сохраняют JWT.*

## Привязка Telegram-аккаунта к аккаунту сайта

*Реализовано на существующих `telegram_link_codes` и `users.telegram_id`, без изменения схемы.*

Задача: связать ученика на сайте с его Telegram, не прося вводить пароль в боте. Решение — одноразовый код в ссылке на бота (deep-link).

```mermaid
sequenceDiagram
  actor U as Ученик
  participant W as Сайт
  participant A as API
  participant T as Telegram
  participant B as Бот

  U->>W: «Привязать Telegram»
  W->>A: POST /telegram/link-code (JWT)
  A->>A: случайный код, срок 10 минут,<br/>запись в telegram_link_codes
  A-->>W: ссылка t.me/<бот>?start=<код>
  U->>T: открывает ссылку → «Start»
  T->>B: /start <код>, telegram_id ученика
  B->>A: POST /telegram/link {код, telegram_id}<br/>X-Service-Token
  A->>A: код существует и не истёк?<br/>users.telegram_id = telegram_id,<br/>код удаляется
  A-->>B: имя ученика
  B-->>U: «Готово! Словарь с сайта доступен здесь»
```

Почему так безопасно:
- код **одноразовый** и живёт **10 минут** — перехваченная старая ссылка бесполезна;
- код **случайный** (`secrets.token_urlsafe(32)`, 43 символа — Telegram допускает в параметре `start` до 64 символов `A–Z a–z 0–9 _ -`), подобрать его нельзя;
- привязать аккаунт может только бот: запрос `/telegram/link` принимается лишь со служебным токеном, который хранится в `.env` и не попадает в код и в git;
- `users.telegram_id` уникален — один Telegram нельзя привязать к двум аккаунтам.

После привязки бот вызывает те же адреса API, что и сайт (`/vocabulary/review`, `/vocabulary/{id}/reviews` и т. д. — см. `docs/api-vocabulary.md`), но со служебным токеном и заголовком `X-Telegram-ID` вместо JWT.
Код хранится как SHA-256; новая ссылка отменяет предыдущую. Погашение кода и запись
связи атомарны. Блокировка пользователя и уникальность Telegram ID защищают гонки.
Существующие связи не заменяются. `GET /telegram/status` показывает статус на сайте.
Демо сохраняется отдельным режимом. Запуск и ограничения — `bot/CONNECTED-WINDOWS.md`.

## Почему монолит, а не микросервисы

| Критерий | Модульный монолит | Микросервисы |
|---|---|---|
| Развёртывание | Один контейнер сервера | Отдельный контейнер, конфигурация и мониторинг на каждый сервис |
| Данные | Одна БД, связи защищены внешними ключами | База на сервис; связи между сервисами — только через API, целостность приходится обеспечивать вручную |
| Запрос «слабые места ученика» | Один SQL-запрос с JOIN по ошибкам, ответам и темам | Сбор данных из нескольких сервисов по сети |
| Отладка и тесты | Один процесс, тесты на одной тестовой базе | Нужно поднимать несколько сервисов и эмулировать сеть |
| Команда | 3 человека, 1 семестр | Оправданы, когда разные команды независимо выпускают свои части |

Для команды из трёх человек на один семестр микросервисы добавили бы сложность без выгоды. Особенно мешало бы разделение базы: адаптивность построена на запросах, которые объединяют таблицы разных модулей.

При этом монолит **модульный**: у модулей чёткие границы, и при росте нагрузки отдельную часть можно вынести в сервис. Первый кандидат — модуль `llm`: запросы к языковой модели медленные и дорогие, их удобно масштабировать отдельно.

## Развёртывание

`docker compose up -d` запускает четыре контейнера:

| Сервис | Образ | Порт | Что делает при старте |
|---|---|---|---|
| `db` | `postgres:16` | 5432 | Данные хранятся в томе `pgdata` и переживают перезапуск |
| `api` | `backend/Dockerfile` | 8000 | Применяет миграции (`alembic upgrade head`), затем запускает сервер |
| `web` | `node:20` | 5173 | Устанавливает зависимости и запускает сайт; запросы `/api/*` проксирует в `api` |
| `bot` | `bot/Dockerfile` | — | Запускает бота (нужен `BOT_TOKEN` в `.env`) |

Учебный контент загружается отдельной командой: `docker compose run --rm api python -m app.seed`.

Секреты (токен бота, ключ LLM, ключ подписи JWT) хранятся только в `.env`, который не попадает в git; шаблон — `.env.example`.
